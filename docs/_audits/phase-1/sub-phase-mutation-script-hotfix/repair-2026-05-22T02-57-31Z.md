# Mutation-script hotfix — repair complete

## 1. Defect summary

(FACT — parent audit `docs/_audits/phase-1/sub-phase-particle-fluids-sph-water/landing-2026-05-22T01-42-51Z.md`
§ 9.3 row 7 banked observation.)

`tools/testkit/mutation/run-mutation.sh` line 71 (pre-fix) used a
directory-only check on each target's `path`:

```bash
if [[ ! -d "${path}" ]]; then
  echo "FAIL: target ${name} path missing: ${path}" >&2
  exit 1
fi
```

Every prior target's `path` in `tools/testkit/mutation/mutmut-config.toml`
resolved to a directory; the implicit assumption held. The
sub-phase-particle-fluids-sph-water Stage 2 commit `dae7040`
introduced the first file-shaped target —
`sph_water_dfsph_generator` at
`tools/testkit/golden/generator/dfsph_density_evolution.py` — exposing
the assumption as a defect at CI time. The wrapper's pre-check rejected
the target with `FAIL: target sph_water_dfsph_generator path missing:
tools/testkit/golden/generator/dfsph_density_evolution.py` even though
mutmut itself accepts both file and directory paths for
`--paths-to-mutate`.

This is a TOOLING defect, NOT a substance defect. The audit's
kill-rate measurement at sub-phase-particle-fluids-sph-water Stage 2
§ 7.6 is valid (the agent's local run reached the actual mutmut
invocation through a direct CLI call that bypassed the wrapper's
validator); only the CI wrapper's pre-check was failing.

## 2. Repair shape

Single-character change at the validator: `[[ ! -d "${path}" ]]` →
`[[ ! -e "${path}" ]]` (existence check; accepts both files and
directories).

Rationale: mutmut accepts both path shapes for `--paths-to-mutate`.
The validator's job is to confirm the target's path resolves to
something that exists, NOT to constrain the shape (file vs directory
is mutmut's concern). Changing to `-e` preserves the safety check
(catches typos, missing files) without imposing the shape constraint.

The repair commit also adds a 6-line explanatory comment block in
`run-mutation.sh` citing the surfacing sub-phase + commit `dae7040`
so future readers see the rationale at the source level.

### 4.1 What the tests assert

Three new tests at `tools/integrity/tests/test_run_mutation_validator.py`
(parallel pattern to replay-tool-hotfix test_replay_prior_phase.py):

1. **`test_run_mutation_validator_uses_existence_check_not_directory_only`**
   — load-bearing source-level assertion. Greps run-mutation.sh
   source for `[[ ! -X "${path}" ]]` and asserts the flag is `e`
   (existence). Fast (no subprocess); deterministic; catches any
   future regression at the source level. Failure messages name the
   offending flag explicitly.

2. **`test_run_mutation_baseline_passes_with_current_config`** —
   end-to-end. Runs `bash run-mutation.sh --baseline` in subprocess
   against HEAD's live `mutmut-config.toml` (which includes the
   file-shaped `sph_water_dfsph_generator` target). Asserts exit 0
   + no `FAIL: target` in stderr + expected `N target paths
   validated` progress line. Cleans up the test-induced
   `baseline-<UTC>.json` artifact afterwards (regardless of
   pass/fail outcome) so the repo stays clean.

3. **`test_run_mutation_validator_rejects_truly_missing_path`** —
   safety check. Mirrors the post-fix validator logic against a
   path under `tmp_path` that doesn't exist; asserts exit 1. Guards
   against an over-relaxed widening from "directory-only" to
   "always pass" — typo'd paths in mutmut-config.toml should still
   surface as FAILs.
