The particle-fluids-sph-water sub-phase Stage 1 surfaced R18
STOP-AND-SURFACE at HEAD `7880135`: even after R12 (raise pre-commit
ceiling) and R16 → R17 (replace O(N²) cell-list with scipy.cKDTree +
pair-array fast path), the canonical 1M-particle SPH capture ran 217
minutes at 100% CPU before being killed past the 10⁴ s threshold.
Root cause is Python-interpreter overhead in the per-step numerical
math — not the neighbor query (cKDTree solved that) but the per-pair
force accumulation, density gradient, and DFSPH pressure iteration
that runs through interpreted NumPy at multi-GB array scale per step.

The same Python-interpreter-overhead bottleneck will recur in:
- eulerian-smoke (grid sim);
- lattice-boltzmann-d3q19 (lattice streaming + collision);
- mpm-multimaterial (particle-grid hybrid scatter).

Each will have a canonical-scale numerical hot loop where pure NumPy
is interpretation-bound. Adding numba as project infrastructure NOW
amortizes the dep landing across all future sub-phases.

This is a focused infrastructure hotfix sub-phase, parallel to the
replay-tool hotfix at
`docs/_audits/phase-1/sub-phase-replay-tool-hotfix/repair-2026-05-20T19-06-35Z.md`
(precedent for "focused tooling work, audit-chained, regression-

## 3. Determinism convention

(FACT — `docs/common/numba.md` post-`7693c0e`.)

### Required decorator form

```python
@njit(fastmath=False, cache=True)
def my_hot_loop(...):
    ...
```

Both kwargs MUST be specified explicitly (audit clarity).

### Banned

| Option | Why banned |
|---|---|
| `fastmath=True` | Re-associates FP ops; breaks bit-exactness against pure-NumPy reference. |
| Unguarded `parallel=True` | numba's `prange` has nondeterministic reduction semantics by default; allowed only with explicit per-thread accumulator + deterministic gather + regression-test update. |
| `error_model="numpy"` | No surface affects at HEAD; explicit ban keeps the surface tight. |

### Why the determinism contract is FP-equivalent, not bit-equivalent

(FACT — surfaced during regression-test development; documented at
`tools/testkit/numba_harness/tests/test_numba_determinism.py` module
docstring + `docs/common/numba.md` § 6.)

NumPy's vectorized SIMD code (AVX2/AVX-512 4-or-8-double-wide
accumulators with pairwise summation) and numba's lowered scalar
inner loop (per-pair sequential ops via LLVM) use different
FP-accumulation patterns. The same algebraic formula produces
slightly different bit patterns at large enough N. Even after
aligning operation orders (direct `rx²+ry²+rz²` instead of
`np.linalg.norm` BLAS dnrm2; explicit `d*d*d` instead of `**3`
np.power; scalar `sigma_3d_over_h3` prefactor matching), a residual
~1e-12 drift remains at N=1024 — this is the SIMD-vs-scalar gap and
is not reducible without re-implementing the pure-NumPy reference
in numba-equivalent scalar form (which would defeat the purpose).

The realistic, achievable determinism contract is:

1. **FP-equivalence** between pure-NumPy and numba JIT
   (max_abs_diff < 1e-9 absolute, well below spec's cross-stack
   1e-4 relative).
2. **Bit-deterministic with itself** — numba JIT run-to-run produces
   bit-identical output (this IS the load-bearing same-stack-same-hw
   guarantee).
3. **Cold-vs-warm cache identity** — clearing `__pycache__`
   produces bit-identical output (compiled artifact is consumer-
   invariant).

This is the same FP-equivalent framing the sph-water sub-phase used
for `density_evolution_vectorized` vs the loop variant of
`density_evolution`. The convention is honest about the
SIMD-vs-scalar gap.

  relax the test** — those ARE the project's determinism
