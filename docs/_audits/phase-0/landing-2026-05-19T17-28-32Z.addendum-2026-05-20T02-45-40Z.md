# Phase 0 landing — retroactive addendum: next-phase preflight coverage gap

This is an append-only addendum (per spec § 7.5) to the Phase 0 landing
audit at `docs/_audits/phase-0/landing-2026-05-19T17-28-32Z.md`. The
parent audit's bytes remain frozen; this sibling file documents a
coverage gap identified post-landing and the mechanical fix landed in
the Phase 1 plan.

## 1. The gap

FACT — Phase 0's LANDING (Block 9, commit `85da2fc`) ran
`uv run python tools/dispatch/preflight-phase.py 0` and recorded
ALL PASSED at parent audit § 5 (lines 205–215). It did NOT run the
**successor** preflight, i.e. `preflight-phase.py 1`, against the
landed state before declaring CONFIRMED.

FACT — The first Phase 1 dispatch on 2026-05-20 surfaced four
preflight-phase-1 bugs that Phase 0's LANDING would have caught had it
run the successor preflight: (a) wrong diagnostics paths
(`tools/diagnostics/tier1` instead of nested
`tools/diagnostics/diagnostics/tier1`); (b) wrong integrity module name
(`bit_physics_integrity` instead of `integrity`); (c) wrong pytest
invocation (single repo-root `pytest -W error tools/` instead of
per-member `uv run --directory <member> pytest -W error`); (d) a
runbook gap around `uv sync --extra dev` per workspace member. Full
details are in the preflight hotfix audit at
`docs/_audits/phase-0/hotfix-preflight-phase-1-2026-05-20T01-34-58Z.md`
(commit `b4bb7d4`, ledger entry on line 11).

INFERENCE — The four bugs all predated the Phase 0 LANDING; none were
introduced after the v0.0.0-phase-0 tag. The LANDING's gate set tested
Phase 0's deliverables internally (integrity Cat 1–5 + Cat-X, pytest
per workspace member, adversarial-fixture meta-test, RD-2D thirteen-gate
acceptance) but did not exercise the next-phase preflight as a
forward-looking precondition probe. The bugs were in the preflight
script itself and in the spec/code mismatch in architecture.md § 7.11
/ Appendix D.1, not in any Phase 0 deliverable — but they shipped on
the same tag and were not surfaceable from inside Phase 0's gate set.

## 2. The fix

FACT — `docs/phases/phase-1-plan.md` § 7.3 (Stage 3 prompt) now
contains a new **STEP 5e — Next-phase preflight dry-run** between
the mutation-testing threshold check (STEP 5d) and the phase audit
write (STEP 6). The step runs
`python tools/dispatch/preflight-phase.py 2`, expects the
`prior-phase-tag:v0.1.0-phase-1` check to be the only failing one
(because the Phase 1 tag is operator-pushed in STEP 9 and is not
present at audit-write time), and HALTS on any other failure with
verdict HALTED-ON-NEXT-PHASE-PRECONDITION. The step's verbatim stdout
is required content in the landing audit's body.

FACT — `docs/phases/phase-1-plan.md` § 7.3 STEP 6's body-content
checklist now includes the next-phase preflight outcome as a
FACT-tagged bullet required for the CONFIRMED verdict.

INFERENCE — The fix generalizes: every phase plan's landing dispatch
should run the **successor** phase's preflight as a final gate before
CONFIRMED. The Phase 0 plan template did not include this step; Phase
1's plan now does, and the convention propagates forward via the
"each subsequent phase's landing audit ships its successor's
preflight" pattern documented in
`tools/dispatch/preflight-phase.py` lines 28–29. The
`phase-2-cross-stack-replication.md`, `phase-3-plan.md`,
`phase-4-plan.md`, `phase-5-productization.md`, and
`phase-6-charter.md` plans will need the equivalent step in their
own landing sections; this is queued for the respective phase
dispatches and is recorded as an open item in the pre-Phase-1
cleanup audit (this commit's session).
