FACT — **h5wasm dtype-string gotcha discovered.** h5wasm 0.10.1 uses a
shorter dtype grammar than NumPy:

| h5wasm code | NumPy / h5py | Bytes |
|---|---|---|
| `<d` | `<f8` / `float64` | 8 |
| `<f` | `<f4` / `float32` | 4 |
| `<i` | `<i4` / `int32` | 4 |
| `<q` | `<i8` / `int64` | 8 |

`dtype: "<f8"` silently downcasts a Float64Array to float32 (the
preflight initially failed with `dtype mismatch: expected float64, got
float32` until corrected to `dtype: "<d"`). The CaptureWriter
(`src/capture.ts`) uses h5wasm-native codes throughout; the convention
is pinned in `preflight/README.md` and in `docs/common/ts.md` so
future maintainers don't reintroduce the bug.

FACT — h5wasm 0.10.1 is the current latest stable release on npm
(verified via `npm view h5wasm version` and `npm view h5wasm time
--json` at session open: 2026-03-27 publish date). Matches the plan §
4 pin verbatim; no Pattern-B version-drift adjustment required.

### 1.3 Capture I/O — the cross-stack gate

FACT — `src/capture.ts:CaptureWriter` per § 3.3.7:
- Constructor `new CaptureWriter(manifest, outDir)` deep-clones the
  manifest (via `structuredClone`) so caller mutations don't leak.
- `addStep(step, state, diagnostics?)` records a step's state (one
  ndarray per field) and optional scalar diagnostics.
- `finalize()` opens an h5wasm `File` in write mode, materializes
  `/steps/{N}/state/{field}` + `/steps/{N}/diagnostics/{check}` +
  `/metadata/` (with attrs replicating manifest fields), computes
  SHA-256 of the payload, writes the manifest JSON with the final
  checksum, and returns the manifest path.
- Rejects state arrays that aren't `Float32Array` or `Float64Array`
  with a typed error.
- Selects dtype code `<f` / `<d` from `manifest.config.dtype`
  (`"f32"` → `<f`, `"f64"` → `<d`).
- Diagnostics scalars are written as 0-d datasets (`shape: []`,
  `dtype: "<d"`).
- Metadata `seed` attribute is written with explicit `[seed]`, shape
  `[1]`, dtype `<i` — h5wasm cannot infer the dtype for a bare numeric
  attribute (a quirk documented in `docs/common/ts.md`).

## 2. Design decisions made

INFERENCE — **WebGPU type definitions pinned at `@webgpu/types`
0.1.70.** Latest stable on npm at session open. Provides `GPU`,
`GPUAdapter`, `GPUDevice`, `GPUQueue`, `GPUBindGroupLayout`,
`GPUComputePipeline`, etc. Pulled into tsconfig via `types: ["node",
"@webgpu/types"]`. Bumping to a newer version is a SHIFTED entry in a
future block report.

INFERENCE — **Node 22+ engine pin via `engines.node = ">=22"`.** Spec
§ 7.7 mandates Node 22 LTS as the minimum. Local machine runs Node
24.15.0, which is the current LTS; CI is also pinned to Node 22 (see
`.github/workflows/ts-strict.yml`). Both work because Node 22 is the
floor.

INFERENCE — **`h5wasm/node` (not `h5wasm/web`) import.** The package
exports `h5wasm/node` for Node usage; the cross-stack test runs under
Node so we use that subpath. Browser-side usage will import the root
`h5wasm` and call `h5wasm.ready` before instantiation.

INFERENCE — **Seed attribute is int32, not int64.** Python's writer
casts via `int(...)` which h5py stores as int64 by default. h5wasm
can't infer the dtype for a bare number; passing `[seed], [1], "<i"`
stores it as int32. Spec § 2.7 doesn't pin a width for the metadata
seed attribute (it's a redundant convenience — the manifest JSON's
`config.seed` is the authoritative copy). Block 1's Python reader
reads any integer attr without caring about width. If a future
consumer asserts on int64 width, bumping to `<q` is a one-line edit.

INFERENCE — **Cross-stack test uses `uv run --directory
tools/testkit`.** The testkit's `pyproject.toml` declares the
`bit-physics-testkit` workspace member with `capture` as a top-level
package. Running `uv run --directory tools/testkit python -c "..."`
activates the workspace environment where `from capture import
load_capture` resolves. Falls back to `console.warn + return` when
`uv` isn't on PATH so CI bring-up phases (where `uv` may not be
installed yet) don't break.

INFERENCE — **Hot-reload callback API uses a registration set, not a
single callback.** Multiple consumers (sim shim + UI panel + dev-tools
panel) may all want to know when a shader reloads; one-callback
semantics would force them to chain. The set + unregister-thunk
pattern matches the standard Web event-handler shape.

INFERENCE — **`@webgpu/types` not bundled in `tsconfig.build.json`'s
declaration emit.** `noEmit` is true in the base config; the build
config flips it for `.d.ts` generation. WebGPU types live in
`@webgpu/types` as ambient declarations consumed at build time; they
don't appear in the generated `.d.ts` files. Phase 1+ consumers of
`@bit-physics/common-ts` either install `@webgpu/types` themselves or
import from a TS file that does.

INFERENCE — **Lockfiles + workspace policy file committed.** Both
`common/common-ts/pnpm-lock.yaml` (1526 lines) and
`common/common-ts/preflight/pnpm-lock.yaml` (22 lines) plus the
auto-generated `pnpm-workspace.yaml` (`minimumReleaseAgeExclude` list
for the typescript-eslint 8.59.4 packages pnpm flagged as recent) are
committed. The `ts-strict.yml` workflow at line 30 expects
`pnpm-lock.yaml` for `--frozen-lockfile` and at line 22
`cache-dependency-path: common/common-ts/pnpm-lock.yaml`, so the
lockfile must ship with the package.

INFERENCE — **`run-cli.mjs` deferred / not shipped.** I attempted to
write a standalone `node examples/hello-physics/run-cli.mjs` runner for
ad-hoc local capture generation but Node's experimental TypeScript
stripper doesn't handle the `.js` extension import convention. The
two Vitest tests cover the same ground (capture write + cross-stack
read), so no CLI driver is required for Phase 0. Phase 1+ may want one
when interactive sims need a `pnpm run sim:rd-2d` shape.
