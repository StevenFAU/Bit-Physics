## § 3 — M5 (cutover) — RE-CHARACTERIZED (Hard-Rule-2)

The planned committed-root-`.lfsconfig` cutover is **mechanically unreachable**:
git-lfs ignores `lfs.standalonetransferagent` + `lfs.customtransfer.*.path` from an
in-repo `.lfsconfig` (arbitrary-binary-execution protection), honoring them only from
the user's trusted `.git/config`. Verified on git-lfs 3.4.1 (local) + 3.7.1 (CI).
Per the charter **AMENDMENT — Stage 1c / M5** (`docs/phases/sub-phase-lfs-architecture.md:117`,
governing § 6 M5 at line 403):

- **R2 is opt-in via trusted `.git/config`** — CI per-job (`setup-lfs-s3.sh`), local
  via a one-command bootstrap (`tools/lfs/README.md`). No root `.lfsconfig` committed.
- **The bandwidth goal is met** by the per-job model (shipped Stage 1b, proven at scale
  by M3/M4); universal-R2-default was never load-bearing and required subverting the
  git-lfs security feature.
- **D4 (GitHub-LFS fallback) is steady-state**, not transitional — fresh clones work
  without R2 creds. **M6** (R2-only) is deferred indefinitely (out of this sub-phase).
- **Architectural finding (banked):** per-job opt-in + GitHub-LFS fallback is *more
  robust* than universal-default routing would have been. The original M5 plan was
  implicitly trying to subvert a correct git-lfs security design.
- **Consequence for the planned commit chain:** the "drop per-job lfs-s3 setup"
  commit was intentionally **not made** — the per-job setup is the only thing that
  activates R2 in CI; removing it would break the strict workflows' R2 fetch.
