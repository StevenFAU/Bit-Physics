## 1. Purpose

Bring the verified SPH water stack to the site as an interactive, screen-space-rendered WebGPU instrument that **proves its correctness** rather than merely looking like water. The moat versus the many pretty-but-uncertified web fluid toys is a PROVE layer no competitor has (§ 2.2 — the survey found **zero** browser fluid demos making any correctness claim, and **zero** DFSPH implementations on the open web): a **live golden-value kernel readout** (the cubic-spline W(r,h) evaluated on the visitor's GPU against the committed golden table), a **pointwise reproduction of the committed 100K canonical capture** (real per-particle + per-density match — possible *because* the canonical scene is non-chaotic, § 2.0), a **spatial-hash ≡ brute-force bit-identity proof** (integer fixed-point atomics make the optimized neighbor search byte-identical to the O(n²) oracle), an **in-page f64 reference mirror** (TypeScript IEEE-f64 mirror of the Python reference, cross-checked at build time, then compared live against the WGSL f32 port), a **DFSPH density/divergence-error convergence plot**, a **kernel-normalization unit-volume check** (∑W·V → 1), and a **run-twice determinism hash**. The water the visitor pours and splashes is driven by a solver whose primitives are the gated code paths.

## 2. Why this sim (and positioning)

### 2.0 What the reference and capture actually are (v0.2 review findings — load-bearing)

The v0.1 draft mischaracterized both. Verified against the code and the committed HDF5 on 2026-07-04:

- **FACT (Phase-1-scope reference).** `packages/sph-water/sph_water/reference/dfsph.py` contains the cubic-spline kernel + gradient, neighbor lists (cKDTree + cell-list), density, SPH continuity (dρ/dt, Bender–Koschier 2015 eq. (5)), and `divergence_free_solve` — a **simplified divergence corrector** (symmetric pairwise correction scaled by ½(dρᵢ/dt − dρⱼ/dt), fixed cap + ≤-tolerance semantics). There is **no constant-density solver, no α stiffness factors, no EOS, no boundary handling, no viscosity force** (the 0.01 in `canonical_params()` is declared but unused by any force). The full dual solver is explicitly deferred to Phase-2+ Stack-C in the module's own docstrings.
- **FACT (the capture is closed-form, not chaotic).** The canonical `_canonical_step` in `packages/sph-water/sph_water/sim.py` computes dρ/dt and **discards it** — the integrator is explicit Euler + gravity only. All particles start at rest and receive identical velocity increments, so the cloud **translates rigidly**: measured across the committed capture, per-axis displacement spread < 5e-12 and the per-particle density fields at step 0 and step 1000 agree to < 1e-11. Mean density is 114.79 (a sampling cloud, not water at ρ₀=1000). The descriptor says "dam-break"; the honest description is *a seeded uniform cloud in free fall, with the verified density pipeline evaluated at every checkpoint*. The demo states this plainly (§ 4.2).
- **INFERENCE (this is good news for the gate).** v0.1 rejected a per-particle capture match "because chaos" — that objection is **refuted for this capture**. A rigid free-fall trajectory and a frame-constant density field are exactly reproducible by an f32 port within a small, measurable tolerance, and the 11 committed checkpoints each carry a **100K-particle f64 density field** — a committed, chaos-free, full-scale verification artifact for the kernel + neighbor search + summation. The v0.1 "settled-state robust observables (rest height, settled histogram)" gate is **deleted** — nothing settles in this capture (no walls) — and replaced by the pointwise match (§ 2.1).
- **FACT (two-tier honesty is required).** A visually convincing dam-break needs pressure forces and walls, which the Phase-1 reference does not verify. So the live playground solver (full DFSPH + boundaries + viscosity, § 3.2) is **beyond-reference by construction** and must be labeled as such in-demo, while the gate binds only to what is committed. This is the first web port where the live solver exceeds the committed reference — the honesty boundary is load-bearing and teachable (§ 4.2).

### 2.1 Lane & gating decision

Authors a new WGSL kernel. The gate is **`new_canonical`**, composed of chaos-free criteria, every one bound to a committed artifact:

- **Closed-form exactness:** the browser evaluates the cubic-spline kernel at the golden-table sample points and matches `tools/testkit/golden/tables/cubic-spline-kernel.json` to golden tolerance; and matches `tools/testkit/golden/tables/particle-fluids/dfsph-density-evolution.json` on the two-particle continuity fixtures. The kernel-normalization invariant (∑W·V → 1 on a lattice) runs on the GPU.
- **Pointwise canonical-capture reproduction (NEW in v0.2, replaces "robust observables"):** the browser replays the canonical scene (committed f32 IC from the data spine, 1000 explicit-Euler gravity steps — matching the reference integrator exactly) and computes the **density field at each of the 11 checkpoints** with the optimized grid search. `_gate_sph_water` in `tools/productization/web-deploy/verify.py` compares position/velocity/density **pointwise against the committed HDF5** on a committed deterministic index subsample (§ 5, driver-payload budget), within measured-then-declared f32↔f64 tolerances. Integration steps are gravity-only (as in the reference), so the CI cost is 11 density evaluations at 100K — tractable under headless lavapipe.
- **Optimized-search ≡ oracle bit-identity:** at moderate N, the grid + counting-sort neighbor search produces a byte-identical density field to the O(n²) brute oracle — SHA-256 match (the boids brute≡sort analog; real because binning/accumulation uses integer fixed-point atomics, § 3.3; DFSPH's gather-only loops need no atomics at all, which strengthens the claim).
- **f64 mirror cross-check:** the in-page TypeScript f64 mirror of the reference (kernel, density, continuity, corrector — IEEE f64, mirrored summation order) matches build-time-committed Python outputs on the fixtures (SHA over canonical bytes), and the WGSL f32 port matches the mirror within measured tolerance at small N (§ 4.3).
- **Run-twice determinism:** same-device replay byte-identical.
- **Live-solver diagnostics are Tier-2** (§ 4.3): DFSPH density/divergence error driven below tolerance each step, mass conservation — surfaced honestly as self-consistency evidence for the beyond-reference solver, not as gate criteria.

**Registration cost (corrected in v0.2):** `GATE_KIND` must be edited in **two places** — `tools/productization/web-deploy/pipeline.py` (dict at line 53) **and** `tools/productization/web-deploy/verify.py` — plus `_gate_sph_water` in `tools/productization/web-deploy/verify.py` and measured `T_SPH_*` tolerance constants (the category defaults already exist: `[overrides.sph-water]` → `[defaults.sph]` rel 1e-4 in `tools/testkit/equivalence/tolerance.toml`). `window.__bitPhysicsReady` is a per-sim `main.ts` global the headless driver polls, not a `common/common-web` export. The web-deploy validate job must **LFS-fetch the 61.7 MB capture** (the pypi-release selective-LFS starvation incident is the precedent — verify the include pattern covers `captures/sph-water-ref/`).

### 2.2 Prior art & positioning (web + literature survey; primary sources re-verified 2026-07-04)

**The solver lineage (what the live solver implements):**
- **Bender & Koschier 2015/2017**, DFSPH (SCA '15, [DOI 10.1145/2786784.2786796](https://doi.org/10.1145/2786784.2786796); [TVCG '17 PDF](https://dankoschier.github.io/resources/papers/BK17.pdf)) — dual solver (constant-density + divergence-free). Verified numbers (Table 1/2, identical in both versions): on the 125K breaking dam at Δt=4 ms, avg **4.5** constant-density + **2.8** divergence-free iterations vs IISPH's **50.5**; total speedups at Δt=4 ms: **6.9× vs IISPH, 13.4× vs PBF, 23.9× vs PCISPH** (v0.1's ">20× over PCISPH/PBF" overstated PBF; and the advantage shrinks toward ~1× at Δt ≤ 0.5 ms — the large-timestep qualifier is essential). Max *local* divergence error 1.9 s⁻¹ vs IISPH's 108.3 (dam break). PCISPH "became totally instable" is the 2017 wording, on the 27K falling-cube scene. **The most iteration-efficient stable incompressible SPH, and per the SPH tutorial "the best overall performance of all discussed PPE variants."**
- **Koschier, Bender, Solenthaler, Teschner** — the Eurographics SPH tutorial ([arXiv:2009.06944](https://arxiv.org/abs/2009.06944)) — added in v0.2 as the canonical modern survey: CFL Δt ≤ λ·h̃/‖v‖_max with λ ≈ 0.4, XSPH viscosity (its eq. (103)), boundary-handling survey (Akinci et al. 2012 particles "most popular"), and the σ₃ = 8/(πh³) *support-h* kernel convention — which is **NOT** the repo's convention (§ 3.3 trap).
- **Monaghan 1992/2005** — the cubic-spline kernel. **Convention (v0.2 correction):** Monaghan 2005 ([DOI 10.1088/0034-4885/68/8/R01](https://doi.org/10.1088/0034-4885/68/8/R01)) writes the M4 spline with **support 2h** (3D prefactor 1/(4πh³) in the (1/6)-form, ≡ σ₃ = 1/(πh³) in the repo's form). The repo golden table (W(0)=1/π at h=1, samples to q=2) is this convention. SPlisHSPlasH and most graphics code use support-h with σ₃ = 8/(πh³) — a silent factor-of-8/scale mismatch if code is ported without re-deriving.
- **SPlisHSPlasH** ([Bender, GitHub](https://github.com/InteractiveComputerGraphics/SPlisHSPlasH)) — the reference SPH library (by name, not vendored). Its `CubicKernel` is support-h — see the trap above.
- **Carensac, Pronost & Bouakaz 2022** ([DOI 10.1007/s00371-021-02379-w](https://doi.org/10.1007/s00371-021-02379-w)) — added in v0.2; this single paper is the actual primary source for **two** v0.1 claims that were mis-attributed: (a) **DFSPH warm-start cyclic instability** ("the warm-start reduces the computation time but introduces a cyclic instability… cyclic compression–decompression motion") — Bender & Koschier themselves present warm start only as a ~3× win; (b) **space-filling-curve cell ordering on GPU**: Morton = no gain (GeForce, 302.8 vs 294.7 ms), Hilbert ≈ 3% (GeForce) to ~10% (Quadro) — marginal, single-implementation study.

**The real-time alternative (rejected for the gated path):**
- **Macklin & Müller 2013**, Position-Based Fluids ([preprint](https://mmacklin.com/pbf_sig_preprint.pdf)) — confirmed verbatim: "we use the Poly6 kernel for density estimation, and the Spiky kernel for gradient calculation" — **not the cubic spline**, so PBF does not inherit the golden tables. Rejected-with-cause (§ 9). Perf framing corrected: the 100K dam break runs **4 sub-steps × 4.3 ms/sub-step per 16 ms frame** on a GTX 680 (v0.1 implied 4.3 ms covered the frame).

**GPU neighbor search:**
- **Green, "Particle Simulation using CUDA"** ([NVIDIA PDF](https://developer.download.nvidia.com/assets/cuda/files/particles.pdf), live) — uniform grid + sort, 27-cell scan. Note: its cell size = particle diameter is the *collision* sizing; for SPH the cell size is the **kernel support radius** (= 2h in the repo convention, § 3.3 — v0.1 said "= h", wrong under our convention).
- **Hoetzlein, "Fast Fixed-Radius Nearest Neighbors" (GTC 2014)** ([PDF](https://ramakarl.com/pdfs/2014_Hoetzlein_FastFixedRadius_Neighbors.pdf); the on-demand.gputechconf.com URL is dead) — counting sort beats radix for grid binning: **15 → 4 kernel calls/frame** (v0.1 said 16→5), 16,384 → 193,487 particles at 32 fps on the same GTX 460M (11×). No Morton (Carensac 2022, above).

**WebGPU peers (all sources read; none makes any correctness claim):**
- **[matsuoka-601/WebGPU-Ocean](https://github.com/matsuoka-601/WebGPU-Ocean)** — SPH (Müller 2003 + Clavet near-pressure — a *weaker/cheaper* solver than DFSPH) capped **~30K real-time on an iGPU** (Ryzen 7 5825U); MLS-MPM reaches ~100K iGPU / ~300K dGPU ([Codrops 2025-02-26](https://tympanus.net/codrops/2025/02/26/webgpu-fluid-simulations-high-performance-real-time-rendering/)). - **[matsuoka-601/Splash](https://github.com/matsuoka-601/Splash)** — the modern quality bar: **narrow-range filter in WGSL** (`render/narrowRangeFilter.wgsl` — port target, § 3.5), raymarched density-grid shadows, ~**70K particles on an iGPU / ~180K on an RTX 3060 laptop** (author, Show HN). **[WaterBall](https://github.com/matsuoka-601/WaterBall)** — half-resolution SSFR (the single biggest render lever), velocity-stretched sprites, depth-gradient edge foam.

- **Platform:** WGSL still has no float atomics (fixed-point i32 is both faster than CAS-loop emulation and *deterministic* — an asset, not a workaround). **Subgroups shipped in Chrome 134**; `shader-f16` is broadly available — both are progressive enhancements only (§ 3.6).

**White space (positioning, re-verified).** (a) **No DFSPH exists on the open web** — GitHub search returns zero repos; the strongest browser solvers are PBF and MLS-MPM. (b) **No browser fluid demo makes any correctness/verification claim** — searches for verification/golden/oracle-equivalence web demos found none. (c) **No WebGPU fluid ships a named scene-preset gallery** — they ship one scene + sliders. The defensible novelty is the intersection: *the first browser DFSPH, Splash-class screen-space water, a template gallery, and a live verification instrument bound to committed artifacts* — uncontested on all four axes.

## 3. Algorithm & accuracy architecture

**Two tiers, one WGSL codebase.** The gated verified core (§ 3.1) and the live solver (§ 3.2) share the same kernel/density/continuity/grid WGSL functions — the primitives inside the live solver are literally the gated code paths.

### 3.1 Gated verified core (ports the reference exactly)
- **Kernel:** 3D Monaghan cubic spline W(r,h) + gradient, **support 2h, σ₃ = 1/(πh³)** — ported line-for-line from `packages/sph-water/sph_water/reference/dfsph.py`, matched to `tools/testkit/golden/tables/cubic-spline-kernel.json` on-GPU.
- **Density & continuity:** ρᵢ = ∑ mⱼW (self-term included, as the reference); dρᵢ/dt = ∑ mⱼ(vᵢ−vⱼ)·∇W — matched to the two-particle golden fixtures.
- **Reference corrector:** the simplified `divergence_free_solve` semantics (fixed cap, ≤-tolerance, symmetric ½(dρᵢ/dt−dρⱼ/dt) correction) — fixture-verified against build-time f64 outputs computed by the repo venv (data spine, § 5).
- **Canonical integrator:** explicit Euler + gravity (what the capture actually ran, § 2.0) — drives the pointwise capture-reproduction gate.
- **f64 mirror:** a TypeScript mirror of kernel/density/continuity/corrector in IEEE f64 with the reference's exact summation order — bit-comparable to NumPy f64 on fixtures (polynomials + sqrt only; no transcendentals), committed expected outputs in the data spine. Used in PROVE for the live f32↔f64 cross-check at small N.

### 3.2 Live full-DFSPH solver (beyond-reference — labeled)
- **The dual solver** (Bender & Koschier 2015/2017): per-particle factor αᵢ = ρᵢ / (|∑ⱼmⱼ∇Wᵢⱼ|² + ∑ⱼ|mⱼ∇Wᵢⱼ|²); constant-density solve (correct ρ* → ρ₀) + divergence-free solve (correct dρ/dt → 0), each a fixed-cap iterate-to-tolerance loop (the 2–20-iteration sweet spot; fixed caps are also the determinism prerequisite). **Warm-start OFF by default** (cyclic compression–decompression instability, Carensac 2022 — operator-flippable, § 10).
- **Non-pressure forces:** gravity; **XSPH viscosity** (SPH tutorial eq. (103)) as the v1 viscosity — cheap, stable, honest about being non-physical; explicit-Laplacian viscosity and surface tension deferred (§ 9).
- **Boundaries:** v1 = analytic SDF walls + sphere/box obstacles (position projection + velocity response with restitution/friction) — the standard web-demo approach; Akinci boundary particles deferred (§ 9). Boundary handling is part of the beyond-reference label — the reference has none.
- **Timestep:** CFL λ ≈ 0.4 (live display of the CFL number is an EXPLAIN feature); pinned dt for deterministic presets.
- **Honesty label (in-demo, verbatim intent):** *"The kernel, density, continuity, corrector, and neighbor search inside this solver are the gated, capture-verified code paths. The full DFSPH pressure loops, walls, and viscosity go beyond the committed Phase-1 reference; their evidence is the Tier-2 live diagnostics below, not the gate."*

### 3.3 Neighbor search (performance-critical, verification-critical)
- **Uniform grid, cell size = kernel support radius = 2h** (v0.2 correction — the repo kernel's support is 2h; sizing cells at h would miss neighbors); 3×3×3 stencil iterated as **9 row-merged contiguous ranges** (WebGPU-Ocean/Hoetzlein pattern).
- **Counting-sort binning** (Hoetzlein): `atomicAdd` cell histogram → exclusive prefix-sum → scatter, then a **full reorder of particle state into cell order** (~2× memory-coherence win; piellardj/WebGPU-Ocean/Hoetzlein all do this). The scan is the **two-level Blelloch scan already designed for `packages/boids-2d`** — ported in-repo, no npm dependency (§ 7).
- **Determinism:** integer atomics are associative ⇒ binning is order-independent; per-particle *gather* loops iterate the reordered cell ranges in a deterministic order ⇒ **bit-identical to the O(n²) oracle walking the same order** ⇒ the hash≡brute proof is real. Any scatter-style accumulation (none needed for DFSPH's gather formulation; thickness/foam splats are render-only) uses fixed-point i32 (×1e7, WebGPU-Ocean-verified pattern).
- **No Morton/Z-order** (Carensac 2022: no GPU gain; § 9).

### 3.4 Precision & determinism posture
**f32 solver state; integer fixed-point atomics for binning.** Posture: **device-scoped bit-exact** (same-seed same-device run-twice) + **cross-device distributional** — cross-device bit-exactness is NOT claimed (per-vendor FP contraction/rounding; the live scenes are chaotic). The boids honest boundary, stated in-demo. The *gate* scene is non-chaotic, so its f32↔f64 tolerance is small and measured — but it is still a tolerance, not a SHA, across devices.

### 3.5 Screen-space rendering (pure aesthetics — never affects the gate)
v0.2 rewrites this section from primary sources + shipped WGSL (attribution corrected: **curvature-flow smoothing is van der Laan/Green/Sainz 2009's contribution** ([DOI 10.1145/1507149.1507164](https://doi.org/10.1145/1507149.1507164)); the bilateral recipe v0.1 attributed to it is actually **Green, GDC 2010** ([slides](https://developer.download.nvidia.com/presentations/2010/gdc/Direct3D_Effects.pdf)); and the **narrow-range filter is promoted to v1** — Truong & Yuksel 2018 ([PACMCGIT, DOI 10.1145/3203201](https://doi.org/10.1145/3203201)) measures it at bilateral cost with strictly better silhouettes, and Splash provides a WGSL reference):
1. **Opaque scene** (container, obstacles) → background color + scene depth.
2. **Particle depth** at **half resolution** — instanced camera-facing quads (WebGPU has no point size), sphere-impostor math (discard outside circle, N.z = √(1−r²), `frag_depth` from the view-space-offset reprojection), depth-tested against scene depth; eye-space depth in `r32float`.
3. **Narrow-range filter**: 2 × separable-1D + 1 × 5×5 2D clean-up, δ = 10r, μ = r, dynamic range adjustment, depth-adaptive world-constant kernel radius clamped ≤ 50 px.
4. **Thickness + foam channel** at half/quarter resolution (`rg16float`, additive Gaussian splats, depth-tested, no depth write): r = thickness, g = the foam signal (§ below).
5. **Composite** at full resolution: normals via choose-smaller-difference central differences (the GDC-2010 "hack", used by every shipped implementation); Schlick Fresnel **F₀ = 0.02**; refraction = background UV perturbed by N.xy · thickness; **Beer–Lambert** per-channel absorption, k ratio ≈ (9 : 3.5 : 1) scaled to taste (WebGPU-Ocean ships k ≈ (1.37, 0.54, 0.15)); HDR cubemap reflection; Blinn specular (~exp 250); write `frag_depth` so late-drawn scene elements compose correctly.
- **Foam for near-zero cost** (v1, replaces v0.1's deferred-everything): depth-gradient edge whitening (WaterBall: maxΔz > 1.5·d), thin-thickness whitening, and a velocity/|Δv| foam channel splatted in pass 4. **Ihmsen 2012 secondary particles stay deferred** — and its classification is by **fluid-neighbor count** (<6 spray, >20 bubbles), *not* Weber number (v0.1 miscite; the paper explicitly declines Weber).
- Fluid-behind-glass is a known structural SSFR limit — open-top container, glass drawn after the fluid.
- **Optional garnish tier (perf-gated):** projected animated caustic texture masked by the thickness footprint; Splash-style raymarched shadows through a coarse density grid (v2).

### 3.6 Performance architecture & budget (the "many effects on screen" requirement)
- **Live N is adaptive by measured capability** (timed probe at first load, not UA sniffing): **floor 8K (any WebGPU device) / target 30K iGPU / 60–100K+ dGPU** — calibrated against the modern bar (WebGPU-Ocean 30K weak-SPH iGPU; Splash 70K iGPU; DFSPH's iterative solves are heavier per step but need fewer, larger steps). The 100K canonical is **offline/CI-gate-only** (integration is gravity-only there, so it is *cheaper* than one live DFSPH frame).
- **Budget split per frame (iGPU target):** solver ≤ 10 ms (grid rebuild + reorder + α + 2 pressure loops at fixed caps), SSFR ≤ 4 ms (half-res depth/thickness + NRF 2+1 + full-res composite), UI/plots ≤ 1 ms. Memory ~40 B/particle state ×2 (ping-pong) + grid ⇒ 100K ≈ ~15 MB — trivial.
- **Workgroup size 64** for particle passes (the surveyed consensus); 256 for scan internals.
- **Progressive enhancements, feature-detected with fallback:** subgroup scan (Chrome 134+), `shader-f16` for render-side textures only (never solver state).
- **Perf checkpoint is step 2 of § 6** — retire the framerate risk before any UI/render investment.

## 4. Scope — four layers

### 4.1 INTERACT
- **Default idle interaction** (the PavelDoGreat lesson: instant response beats feature count): drag anywhere = impulse sphere (push/splash); two-finger / right-drag = orbit camera.
- **Pour / emit** — press-hold spawns a particle stream (faucet); **tilt** — drag a gravity dial or use device orientation on mobile; **domain squeeze** — a wall-position slider (the WebGPU-Ocean signature interaction, nearly free); **draggable sphere obstacle** (SDF collision).
- **Template gallery (data-spine-defined presets — open ground no peer ships, § 2.2):** each a named card with params + caption + citation: **Dam break** (the classic column collapse — the DFSPH paper's benchmark scene), **Double dam** (two columns collide), **Faucet / waterfall**, **Sloshing tank** (tilt-driven), **Hydrostatic column** (still water — watch density error and the ∑W·V check on a resting state), **Zero-G blob** (g=0), **Whirlpool** (orbiting stirrer impulse), **Ball drop** (obstacle splash), **Piston** (domain squeeze), and **"The gate scene"** — the canonical free-fall replay with the live error-vs-committed readout (a preset that IS a verification run — the moat made playable).
- **Sliders:** particle count (adaptive cap), viscosity (XSPH α), gravity, solver iteration caps + tolerance (live loop only; canonical pinned), surface-render vs particle-render.
- **Verification toggles as first-class controls:** brute↔grid search (drives hash≡brute), f32↔f64-mirror comparison at small N, warm-start on/off (watch the Carensac instability yourself — a *teachable failure mode*, § 4.2).

### 4.2 EXPLAIN (equation → code legibility)
- The SPH discretization, the cubic-spline piecewise form **with the support-2h vs support-h convention trap made explicit** (the repo table vs SPlisHSPlasH — real pedagogy, since it is the #1 porting bug in SPH), the continuity equation, and the DFSPH dual solver (α factor + both loops) — each rendered next to the committed WGSL line and the NumPy reference anchor (`packages/sph-water/sph_water/reference/dfsph.py`), snippet anchors extracted at build time (§ 5), HARD-FAIL on drift.
- **Why the kernel must normalize** (∑W·V = 1) — tied to the live diagnostic; **why DFSPH** (few iterations, the verified 4.5+2.8 vs 50.5 numbers) cited to Bender & Koschier; **CFL** λ≈0.4 with a live CFL readout; **XSPH** as honest non-physical smoothing.
- **The two-tier honesty story, front and center:** what the committed Phase-1 reference verifies (kernel/density/continuity/corrector — and exactly how the capture was made, § 2.0, including that its descriptor says "dam-break" while the scene is free-fall), vs what the live solver adds beyond it. **The honest determinism boundary** (device-scoped bit-exact vs cross-device distributional) — the honesty thesis made teachable.
- **A teachable failure mode:** the warm-start toggle + the Carensac 2022 citation — flip it, watch the cyclic compression appear in the density-error plot. PROVE artifacts that can visibly fail are the credibility engine.

### 4.3 PROVE (the moat — every artifact chaos-free or honestly tiered)

**Tier 1 — bound to committed artifacts (the gate):**
- **Live golden-value kernel readout — flagship.** W and |∇W| at the committed sample points on the visitor's GPU vs `tools/testkit/golden/tables/cubic-spline-kernel.json`; max deviation displayed.
- **Canonical-capture reproduction panel.** The gate-scene replay with per-checkpoint max|Δposition| / max|Δdensity| vs the committed f64 capture (subsampled reference values shipped in the data spine), plotted against the declared tolerance. *Per-particle, at 100K, against a committed artifact — no web fluid demo has anything in this class.*
- **Spatial-hash ≡ brute-force bit-identity.** Same particle set through both paths, SHA-256 the density field, show byte-identical. Falsifiability probe: a deliberately-perturbed grid path turns it red.
- **Two-particle continuity fixtures + kernel normalization** (∑W·V → 1 on a lattice) on-GPU.
- **f64 mirror cross-check.** TS-f64 mirror ≡ committed Python outputs (SHA), then WGSL-f32 vs mirror at N ≤ 4K live, max deviation vs declared tolerance.
- **Run-twice determinism hash** + the **verification card**: gate kind, golden-table SHAs, capture provenance (100K, seed 42, dt=0.001, h=0.05, 11 checkpoints, payload SHA `7590149221180f82…`), reference determinism `bit-exact-same-hw`, browser posture device-scoped.

**Tier 2 — live-solver self-consistency (labeled beyond-reference):**
- **DFSPH error-convergence plot:** live max density error + max divergence error vs iteration/step, driven below tolerance (the paper's 1.9 vs 108.3 s⁻¹ max-local-divergence framing quoted honestly as *max local*).
- **Mass conservation** (∑m exact by construction — shown), particle-count integrity, CFL number, warm-start instability demo.

### 4.4 RENDER (visually stunning, physics-honest)
- **Screen-space water** per § 3.5: half-res depth/thickness → narrow-range filter → Fresnel/refraction/Beer–Lambert/cubemap composite + the free foam stack. HDR environment; tone-mapped.
- **Debug/honesty views:** raw particles colored by density / speed / pressure(κ) / neighbor count via `common/common-web/src/colormap.ts`; neighbor-grid overlay; and the SSFR intermediate buffers themselves (depth → filtered depth → thickness → normals) as a **pipeline-explorer strip** — the render made legible, which *is* the honesty aesthetic.
- **hiDPI** at `min(devicePixelRatio, 2)`; poster + motion loop (`tools/productization/web-deploy/web/pages/assets/make-posters.mjs` / `make-loops.mjs`); frame-indexed animation only.

## 7. Governance & constraints

- **Two-tier honesty is a hard requirement:** the live full-DFSPH solver is beyond-reference and must be labeled as such in-demo (§ 3.2 wording); the gate binds only to committed artifacts. Promoting full DFSPH to a verified reference (the Phase-2+ Stack-C arc the reference's own docstrings anticipate) is a separate backend spec.
- **HARD BOUNDARY — no backend changes.** No edits to `packages/sph-water/sph_water/`, the golden tables, the committed capture, or the sim spec-ref. The web build is additive (build-time *reads* of the h5 via the repo venv are fine).
- **Cross-device bit-exactness is NOT claimed** (§ 3.4). Device-scoped bit-exact + cross-device distributional, stated in-demo.
- **Precision:** f32 solver state; integer fixed-point atomics (×1e7 pattern) for binning/splats; f16 render-side only.
- **No new runtime dependencies:** the prefix scan is ported in-repo (boids-2d two-level Blelloch design), not taken from npm; the NRF is ported from the paper with Splash's WGSL as reference. Colormap module consumed, not edited.
- **Frame-indexed animation only; standalone-serve constraint** (all data rides the bundle / per-sim `public/`; no `../../` cross-refs — the validate server serves each sim's dist standalone).
- **Citations:** every backticked `path:line` in this spec and in the demo's EXPLAIN copy uses full repo-root paths (Cat-4 hook + CI `integrity --all` both scan this file).
- **Deploy:** landing card + web-deploy discovery (`package.json` + `src/main.ts` with `exposeCapture` + `createSettingsPanel`); publishing operator-dispatched (`confirm_deploy=true`).

## 9. Out of scope / deferred / rejected-with-cause

- **Any backend change** — reference, invariants, tables, captures, spec-ref frozen.
- **"Robust-observable settled-state gate" — DELETED (v0.2, refuted).** The v0.1 plan gated on settled-dam statistics (rest height, settled histogram); the capture has no walls and never settles (§ 2.0). Replaced by the pointwise capture match, which the same review showed is feasible *because* the canonical is non-chaotic.
- **Per-particle match on live/chaotic scenes — still rejected (chaos).** The v0.1 chaos argument was wrong about the *canonical* but right about live dam-breaks: f32 cannot track f64 through real pressure-coupled dynamics; live scenes get Tier-2 diagnostics, not pointwise gates.
- **PBF for the gated path — REJECTED (kernel mismatch, confirmed at source):** Poly6/Spiky per the paper's own text; does not inherit the cubic-spline golden tables.
- **Morton/Z-order — REJECTED (no GPU gain):** Carensac et al. 2022 (Morton ≈ 0%, Hilbert ≈ 3–10%, single-study caveat). Linear XYZ cell indexing + counting sort.
- **Warm start by default — REJECTED (documented instability):** Carensac et al. 2022 cyclic compression–decompression; shipped as an off-by-default teachable toggle. (Attribution corrected: this is NOT in Bender & Koschier.)
- **100K at real-time — NOT a baseline:** modern bar is Splash's ~70K iGPU with a cheaper solver; DFSPH targets § 3.6 tiers; 100K is CI-only. High-N interactive is MPM's lane (`packages/mpm-multimaterial/web/`).
- **Curvature-flow smoothing — deferred (cost):** ~10× NRF per Truong & Yuksel; NRF ships instead (correctly attributed, § 3.5).
- **Ihmsen secondary particles, Akinci boundaries, ellipsoid splatting, surface tension, real caustics, marching cubes, grid pressure** — deferred/out (§ 5).
